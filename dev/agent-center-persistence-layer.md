# Agent Center Persistence Layer

## Purpose

Agent Center V1 previously used process-local in-memory state. That was enough for local development and single-invocation tests, but it made production validation unreliable on serverless infrastructure: create, fetch, run, and delete requests could land on different instances and lose access to validation runs, fixtures, issues, usage events, or cleanup state.

The persistence layer adds an `AgentCenterRepository` abstraction so Agent Center state can keep the existing local/test behavior while allowing production deployments to switch to a persistent backend.

## Current In-Memory Limitation

The in-memory backend is still the default for local development and tests. It is intentionally process-local and resets when the Node process resets. It should not be used for real merchant pilots where records must survive serverless cold starts, instance drift, redeployments, or multi-region routing.

The specific production limitation this addresses is cross-invocation reliability for:

- internal production validation runs
- internal demo fixture manifests and cleanup
- generated issues and resolution plans
- preview-only usage ledger events
- GMV assurance snapshots

## Repository Abstraction

`AgentCenterRepository` owns the current `AgentCenterState` and exposes:

- `getState`, `replaceState`, `reset`, `persist`
- `list`, `getById`, `upsert`, `deleteById`
- query helpers by `merchant_id`, `store_id`, `scan_target_id`, `issue_id`, `fixture_id`, and `production_validation_run_id`
- `usageEventsBy`
- `snapshotsBy`

Current implementations:

- `InMemoryAgentCenterRepository`
  - default for local/test
  - keeps existing test behavior
- `FileBackedAgentCenterRepository`
  - enabled only with `AGENT_CENTER_STATE_BACKEND=persistent`
  - writes JSON state to `AGENT_CENTER_STATE_FILE`
  - intended as a bridge until the app has a durable database adapter
- `DbAgentCenterRepository`
  - enabled with `AGENT_CENTER_STATE_BACKEND=db`
  - hydrates Agent Center state from Postgres at request start and flushes changed core records at request end
  - requires the Agent Center schema migration in `pivota-backend`

## Environment Config

```bash
AGENT_CENTER_STATE_BACKEND=memory
AGENT_CENTER_STATE_BACKEND=persistent
AGENT_CENTER_STATE_BACKEND=file
AGENT_CENTER_STATE_BACKEND=db
AGENT_CENTER_STATE_FILE=/tmp/pivota-agent-center-state.json
AGENT_CENTER_DATABASE_URL=postgres://...
AGENT_CENTER_DB_SSL=true
AGENT_CENTER_DB_SCHEMA=agent_center
```

Defaults:

- local/test: `memory`
- production: can use `persistent` when explicitly configured

If `AGENT_CENTER_STATE_BACKEND=persistent` or `file` and `AGENT_CENTER_STATE_FILE` is unset, the file-backed repository uses `/tmp/pivota-agent-center-state.json`.

If `AGENT_CENTER_STATE_BACKEND=db`, the portal runtime must have `AGENT_CENTER_DATABASE_URL` and the `agent_center` schema must already be migrated by `pivota-backend`.

## Persisted Objects

The persistence layer is designed around these core records:

- `MerchantStore`
- `ScanTarget`
- `AgenticGMVIssue`
- `ProductUnderstandingDiagnosis`
- `OfferExecutionDiagnosis`
- `CheckoutVerificationDiagnosis`
- `GMVAssuranceSnapshot`
- `IssueResolutionPlan`
- `UsageEvent`
- `ProductionValidationRun`
- `DemoFixture`

The file-backed backend currently persists the whole `AgentCenterState` JSON, including lower-priority trace data such as jobs, runs, scores, parsed recommendations, and match results. A database implementation can choose to store core records first and move raw traces to separate tables later.

## Idempotency Rules

Usage events continue to use deterministic `idempotency_key` values. Repository `upsert` preserves the first matching usage event by idempotency key so reruns and reloads do not duplicate preview credits.

Resolution plan generation remains idempotent per issue unless explicitly regenerated by the caller. Production validation runs keep stable IDs and status across create, run, fetch, and delete calls when the selected repository backend is persistent.

## Production Validation Harness

The internal production validation harness now reads and writes through the selected repository. With a persistent backend enabled:

- `POST /api/internal/agent-center/production-validation-runs` creates a stable run record
- `GET /api/internal/agent-center/production-validation-runs/:id` can fetch after a reload
- `POST /api/internal/agent-center/production-validation-runs/:id/run` updates status, generated IDs, report, snapshot, and usage event IDs
- `DELETE /api/internal/agent-center/production-validation-runs/:id` marks the run deleted and removes tied temporary state

All usage remains `billing_mode = preview_only` and `billing_status = not_invoiced`.

## Demo Fixtures

Internal demo fixture create, fetch, cleanup, and delete also use the repository. Fixture records remain tagged with:

- `demo_fixture = true`
- `fixture_id`
- `created_by = internal`
- `created_at`
- `expires_at` / `ttl_minutes`
- `environment`
- `cleanup_status`

`cleanupExpiredDemoFixtures()` removes tied fixture records and marks the manifest `expired`. Manual delete marks the manifest `deleted`.

## Database Migration Plan

This repo now includes a lightweight Postgres-backed repository adapter using `pg`. Before real merchant pilots, run the `pivota-backend` Agent Center schema migration and configure the merchant portal with a restricted Postgres URL scoped to the `agent_center` schema.

Recommended table groups:

- `agent_center_merchant_stores`
- `agent_center_scan_targets`
- `agent_center_issues`
- `agent_center_product_understanding_diagnoses`
- `agent_center_offer_execution_diagnoses`
- `agent_center_checkout_verification_diagnoses`
- `agent_center_gmv_assurance_snapshots`
- `agent_center_issue_resolution_plans`
- `agent_center_usage_events`
- `agent_center_production_validation_runs`
- `agent_center_demo_fixtures`

Recommended indexes:

- `merchant_id`
- `store_id`
- `scan_target_id`
- `issue_id`
- `fixture_id`
- `production_validation_run_id`
- `product_entity_id`
- `agent_type`
- `provider`
- unique `usage_events.idempotency_key`
- unique `issue_resolution_plans.issue_id` for active non-regenerated plan if one-active-plan semantics are required

JSON columns are acceptable for V1 patches, findings, summaries, reports, and snapshots. Promote high-cardinality query fields to typed columns as pilot usage grows.

## Production Deployment Requirements

For a real pilot:

1. Configure a durable database backend for `AgentCenterRepository`.
2. Enforce unique usage idempotency keys at the database level.
3. Keep internal fixture and production validation routes gated by internal secret and env flags.
4. Keep merchant UI semantics unchanged: show credits and preview usage, not token costs or invoices.
5. Keep all Agent Center usage records `preview_only` / `not_invoiced` until real billing is explicitly implemented.

## Known Limitations

- The file-backed persistent backend is not a durable multi-instance production database. On Vercel, `/tmp` can be instance-local and may not survive redeployments or route traffic consistently across instances.
- The file-backed backend is useful for local reload simulation and single-instance smoke validation only.
- Raw LLM outputs, parsed recommendations, match results, job logs, and verification traces are persisted as part of the full JSON state in the file-backed implementation, but they are still lower-priority for a first DB schema.
- No real billing, PSP authorization, payment, order write-back, settlement, refund, or transaction-fee behavior is introduced by this layer.
